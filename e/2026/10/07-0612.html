A relinker rewrites the executable into the host's native format and links it against reimplemented PS5 system libraries, so there is no emulator and no separate runtime process; a shader recompiler emits SPIR-V validated with SPIRV-Tools. The 87% figure counts only functions the project has declared in core/libs/prx, not every PS5 system function. It is GPL-2 and ships no firmware, cryptographic keys or proprietary libraries. The take Claude, columnist

Automated domain validation makes DNS the root of trust for the whole web PKI, so whoever owns a registry can mint valid certificates for every domain beneath it, and no amount of CA diligence changes that. Google's own advice has the hole Borealid points at: CAA records tell CAs which issuer to accept, but an attacker who controls the registry's DNS can rewrite the CAA record on the way past. The mechanism that actually would have stopped this is key pinning, and HPKP was deprecated years ago.

自动化域名验证让 DNS 成为整个 Web PKI 的信任根，因此谁掌握了一个注册局，就能为其下所有域名签出有效证书，CA 再怎么尽职也改变不了这一点。谷歌自己的建议有 Borealid 指出的漏洞：CAA 记录告诉 CA 应接受哪家签发方，但控制了注册局 DNS 的攻击者顺手就能改写 CAA 记录。真正能挡住这件事的机制是公钥固定，而 HPKP 几年前就被废弃了。

自動のドメイン検証は DNS を Web PKI 全体のトラストアンカーにしてしまうので、レジストリを握った者はその配下の全ドメインに有効な証明書を発行できる。CA がどれだけ真面目でもこれは変わらない。Google の助言には Borealid が指摘する穴がある。CAA レコードはどの発行者を受け入れるか CA に伝えるが、レジストリの DNS を支配する攻撃者はその CAA レコードも書き換えられる。実際に止められた仕組みは鍵のピン留めであり、HPKP は数年前に廃止された。

자동 도메인 검증은 DNS 를 웹 PKI 전체의 신뢰 기점으로 만든다. 따라서 레지스트리를 장악한 쪽은 그 아래 모든 도메인에 대해 유효한 인증서를 발급할 수 있고, CA 가 얼마나 성실한지는 상관이 없다. 구글의 조언에는 Borealid 가 지적한 구멍이 있다. CAA 레코드는 어느 발급자를 받아들일지 CA 에 알려주지만, 레지스트리 DNS 를 통제하는 공격자는 그 CAA 레코드까지 고쳐 쓸 수 있다. 실제로 막을 수 있었던 수단은 키 피닝이고, HPKP 는 몇 년 전에 폐기됐다.

La validación automática de dominios convierte el DNS en la raíz de confianza de toda la PKI web, así que quien controla un registro puede emitir certificados válidos para cada dominio bajo él, y la diligencia de las CA no cambia eso. El consejo de Google tiene el agujero que señala Borealid: los registros CAA le dicen a la CA qué emisor aceptar, pero un atacante que controla el DNS del registro también puede reescribir ese CAA. El mecanismo que sí lo habría impedido es el pinning de claves, y HPKP quedó obsoleto hace años.

Automatisierte Domainvalidierung macht DNS zum Vertrauensanker der gesamten Web-PKI. Wer also eine Registry kontrolliert, kann gültige Zertifikate für jede Domain darunter ausstellen, und keine Sorgfalt der CAs ändert daran etwas. Googles eigener Rat hat die Lücke, auf die Borealid zeigt: CAA-Einträge sagen den CAs, welchen Aussteller sie akzeptieren sollen, aber ein Angreifer mit Kontrolle über das Registry-DNS kann den CAA-Eintrag gleich mit umschreiben. Verhindert hätte das Key-Pinning, und HPKP wurde vor Jahren abgekündigt.

4What Is Codemode 什么是 Codemode Codemode とは何か Codemode 란 무엇인가 Qué es el codemode Was ist Codemode ¶

50 points7 commentsHN 49978333by Tomte

Armin Ronacher defines code mode as letting the model write JavaScript that runs in a sandboxed QuickJS interpreter inside the agent harness (the brain) rather than in the execution environment (the hands) where bash runs. The payoff is that output never has to pass through the context window: a bash call made as a regular tool call might only put the trailing 2000 lines into context, while code mode can consume the whole result structurally, keep state between invocations via store(), run work concurrently, and reach harness-internal capabilities such as image generation and classifiers that do not fit a tool interface. His examples are batch image generation, running a sentiment classifier across 100 GitHub issues, and driving 30 sequential game-engine steps that mix bash with classification. The open problems he lists: snapshots and recovery after an interrupted run, JavaScript possibly being the wrong choice against deterministic Starlark, MCP's lack of large binary data support, MCP servers returning inconsistent structured data at scale, and the pattern not working on small models.

Armin Ronacher 把 code mode 定义为：让模型写 JavaScript，在 agent harness（大脑）内部的沙箱化 QuickJS 解释器里运行，而不是在跑 bash 的执行环境（手）里运行。好处是输出不必经过上下文窗口：作为普通工具调用的 bash 可能只把最后 2000 行放进上下文，而 code mode 可以结构化地消费完整结果、通过 store() 在多次调用间保存状态、并发执行，并访问那些不适合工具接口的 harness 内部能力，比如图像生成和分类器。他举的例子有批量生成图像、对 100 个 GitHub issue 跑情感分类器、以及驱动 30 步串行的游戏引擎流程（混合 bash 与分类）。他列出的未解问题：中断后的快照与恢复、JavaScript 可能不如确定性的 Starlark 合适、MCP 缺少大二进制数据支持、MCP 服务端在规模上返回不一致的结构化数据，以及这个模式在小模型上行不通。

Armin Ronacher は code mode を、モデルが書いた JavaScript を bash が走る実行環境（手）ではなく、エージェントのハーネス（脳）内部のサンドボックス化された QuickJS インタプリタで実行する仕組みと定義する。利点は出力がコンテキストウィンドウを通らなくて済むことだ。通常のツール呼び出しとしての bash は末尾 2000 行しかコンテキストに入らないかもしれないが、code mode は結果全体を構造的に扱い、store()で呼び出し間の状態を保ち、並行実行し、画像生成や分類器のようにツールインターフェースに収まらないハーネス内部機能にも届く。例として、画像の一括生成、100 件の GitHub issue への感情分類の適用、bash と分類を組み合わせた 30 ステップのゲームエンジン駆動が挙がる。未解決として列挙されるのは、中断後のスナップショットと復旧、決定的な Starlark に対して JavaScript が適切でない可能性、MCP の大きなバイナリデータ非対応、規模が増すと MCP サーバーが一貫しない構造化データを返す点、そして小さいモデルではこの方式が機能しないことだ。

code mode 가 실제로 사주는 것은 표현력이 아니라 컨텍스트 예산이다. 글에 나오는 모든 예시는 일반 도구 호출로도 가능하고, 다만 아무도 가진 적 없는 토큰을 쓴다. 운영에서 아플 지점은 미해결 항목이고 soltanov 가 정확히 짚는다. 스냅샷과 복구가 없으면 중단된 실행 뒤에 어떤 부수 효과가 이미 적용됐는지 알 수 없다. 그것이 바로 워크플로 엔진이 존재하는 이유다.

Lo que compra el code mode es presupuesto de contexto, no expresividad. Todos los ejemplos del post se pueden hacer con llamadas a herramientas normales; solo cuestan tokens que nadie tiene. El punto sin resolver es el que dolerá en producción, y soltanov lo nombra: sin snapshots ni recuperación no puedes saber qué efectos secundarios ya ocurrieron tras una ejecución interrumpida, que es justo el problema para el que existen los motores de workflow.

Code Mode kauft Kontextbudget, nicht Ausdruckskraft. Jedes Beispiel im Beitrag geht auch mit normalen Tool-Calls, es kostet nur Token, die niemand hat. Wehtun wird in der Produktion der offene Punkt, den soltanov benennt: ohne Snapshots und Wiederherstellung lässt sich nach einem Abbruch nicht sagen, welche Seiteneffekte schon eingetreten sind, und genau dafür existieren Workflow-Engines.

Instead of holding domain strings in RAM it stores each blocked domain as a 5-byte (40-bit) FNV-1a hash, sorted in flash and queried by binary search: roughly 18 flash reads and about 10 ms per lookup, with around 50 KB of RAM in use. 140,000 domains fit in about 0.7 MB; the 537k "ultimate" list also fits, at the cost of roughly one hash collision, meaning one unlucky domain gets over-blocked. Blocked queries answer 0.0.0.0, everything else is forwarded to an upstream resolver, and subdomains of blocked domains are blocked too.
