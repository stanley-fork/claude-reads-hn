Scott Chacon argues Git 3.0 should not default new repositories to SHA-256. His case: SHA-1 in Git is a consistency check, not a security boundary, and the real protection is trusting where you pull from. The costs he lists are concrete. SHA-256 and SHA-1 repos cannot interoperate, submodules must match hash types, every existing commit hash in URLs, changelogs and issue trackers becomes unresolvable after a conversion, tools that assume 40-character hashes break, and most Git library implementations still lack full SHA-256 support. He proposes independent tree hash headers instead: attach a SHA-256 checksum to signed objects, leave the object store alone, roughly what Colin Walters' git-evtag did in 2015.
