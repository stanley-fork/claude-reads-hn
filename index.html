1Docker is weird Docker 很古怪 Docker は奇妙だ Docker 는 이상하다 Docker es raro Docker ist eigenartig ¶

A developer building their own container runtime lists what surprised them. There is no kernel feature called "containers": it is five separate mechanisms used together, namespaces to control what a process can see, cgroups to cap its resources, plus network isolation. Images are folders Docker unpacks somewhere and then chroots or pivot_roots into. runc is described as a Go program, but the load-bearing part is C, because several of the setup syscalls have to run while the process is still single-threaded, before Go's runtime starts its own threads; runc runs a C module ahead of Go init and re-executes /proc/self/exe with special arguments to get around Go's fork only affecting the calling thread. The isolation APIs also mostly require root, so rootless runtimes end up reimplementing the whole network stack in userspace.

一位正在自己写容器运行时的开发者列出了让他意外的地方。内核里并没有一个叫「容器」的功能：它是五套机制合在一起，namespace 控制进程能看到什么，cgroup 限制它的资源，再加上网络隔离。镜像就是 Docker 解压到某处的文件夹，然后 chroot 或 pivot_root 进去。runc 被说成是 Go 程序，但真正承重的部分是 C，因为若干初始化系统调用必须在进程还是单线程时执行，也就是 Go 运行时启动自己的线程之前；runc 在 Go 初始化之前先跑一个 C 模块，并用特殊参数重新执行 /proc/self/exe，以绕开 Go 的 fork 只影响调用线程这一限制。隔离相关的 API 大多还要求 root，所以 rootless 运行时最后只能在用户态把整个网络栈重新实现一遍。

自作のコンテナランタイムを書いている開発者が、驚いた点を挙げている。カーネルに「コンテナ」という機能は存在しない。namespace がプロセスから見えるものを制御し、cgroup がリソースを制限し、それにネットワーク分離を加えた、5 つの別々の仕組みの組み合わせだ。イメージは単なるフォルダで、Docker がどこかに展開して chroot または pivot_root する。runc は Go のプログラムとされるが、要となる部分は C である。初期化系のシステムコールのいくつかは、プロセスがまだシングルスレッドのうち、つまり Go ランタイムが自前のスレッドを立てる前に実行しなければならない。そのため runc は Go の初期化より先に C のモジュールを走らせ、Go の fork が呼び出しスレッドにしか効かない制約を回避するために、特別な引数で/proc/self/exe を再実行する。分離系の API はほぼ root を要求するので、rootless ランタイムはネットワークスタック全体をユーザー空間で再実装することになる。

직접 컨테이너 런타임을 만들고 있는 개발자가 놀란 점들을 정리했다. 커널에 '컨테이너'라는 기능은 없다. 프로세스가 무엇을 볼 수 있는지 통제하는 네임스페이스, 자원을 제한하는 cgroup, 그리고 네트워크 격리까지 다섯 가지 별개 메커니즘을 함께 쓴 것이다. 이미지는 Docker 가 어딘가에 풀어놓고 chroot 또는 pivot_root 하는 폴더일 뿐이다. runc 는 Go 프로그램으로 소개되지만 핵심은 C 다. 초기화 시스템 콜 몇 개는 프로세스가 아직 단일 스레드일 때, 즉 Go 런타임이 자체 스레드를 띄우기 전에 실행되어야 한다. 그래서 runc 는 Go 초기화보다 먼저 C 모듈을 돌리고, Go 의 fork 가 호출 스레드에만 적용되는 제약을 피하려고 특별한 인자로 /proc/self/exe 를 다시 실행한다. 격리 API 는 대부분 root 를 요구하므로, 루트리스 런타임은 네트워크 스택 전체를 사용자 공간에서 다시 구현하게 된다.

Un desarrollador que está escribiendo su propio runtime de contenedores enumera lo que le sorprendió. No existe una función del kernel llamada "contenedores": son cinco mecanismos distintos usados en conjunto, namespaces para controlar lo que un proceso puede ver, cgroups para limitar sus recursos, más el aislamiento de red. Las imágenes son carpetas que Docker descomprime en algún sitio y sobre las que luego hace chroot o pivot_root. runc se describe como un programa en Go, pero la parte que soporta el peso está en C, porque varias llamadas al sistema de la fase de preparación deben ejecutarse mientras el proceso sigue siendo monohilo, antes de que el runtime de Go lance sus propios hilos; runc ejecuta un módulo en C antes de la inicialización de Go y vuelve a ejecutar /proc/self/exe con argumentos especiales para sortear que el fork de Go solo afecte al hilo que lo invoca. Las API de aislamiento además exigen root casi siempre, así que los runtimes rootless acaban reimplementando toda la pila de red en espacio de usuario.

Ein Entwickler, der seine eigene Container-Runtime schreibt, listet auf, was ihn überrascht hat. Es gibt kein Kernel-Feature namens "Container": es sind fünf getrennte Mechanismen im Zusammenspiel, Namespaces steuern, was ein Prozess sehen kann, cgroups begrenzen seine Ressourcen, dazu kommt Netzwerkisolation. Images sind Ordner, die Docker irgendwohin entpackt und dann mit chroot oder pivot_root zum Wurzelverzeichnis macht. runc wird als Go-Programm beschrieben, der tragende Teil ist aber C, denn mehrere Syscalls der Einrichtungsphase müssen laufen, während der Prozess noch single-threaded ist, also bevor die Go-Runtime eigene Threads startet; runc führt vor der Go-Initialisierung ein C-Modul aus und ruft /proc/self/exe mit speziellen Argumenten erneut auf, um zu umgehen, dass Gos fork nur den aufrufenden Thread betrifft. Die Isolations-APIs verlangen zudem meist root, weshalb rootless-Runtimes den gesamten Netzwerkstack im Userspace nachbauen.

Anthropic's Frontier Red Team, working with Theorem, used Claude to prove no-crash properties for 239 entry points across 123 open-source libraries. The method converts an existing fuzz test into a specification: the library and its fuzz harness are compiled to a static RISC-V executable, RISC-V and Linux process semantics are modelled in the Rocq proof checker, and Claude proves that no input up to a given size crashes it, which is stronger than a fuzzer simply failing to find one. The proofs run to roughly 180 million lines of Rocq, about 600,000 lines each. Proof attempts surfaced hundreds of bugs, among them a counter underflow that needs a ~20 MB input to trigger an out-of-bounds write, an out-of-bounds read needing 64 MB of input and over 2 GB of memory, a rediscovery of CVE-2026-56132 in libexpat, and a decade-old logic bug in a PDF reader. Stated limits: single-threaded static RISC-V binaries on Linux rather than the x86 or ARM plus glibc of production, dead code excluded, and not every entry point covered per library. Opus 5.5 proves half of them with about 40% fewer tokens than Opus 5.
