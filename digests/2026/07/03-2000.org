** PostgreSQL and the OOM killer: Why we use strict memory overcommit :postgres:linux:kernel:debugging:
:PROPERTIES:
:ID:       48774509
:URL:      https://www.ubicloud.com/blog/postgresql-and-the-oom-killer-why-we-use-strict-memory-overcommit
:HN_URL:   https://news.ycombinator.com/item?id=48774509
:POINTS:   126
:COMMENTS: 49
:BY:       furkansahin
:END:

*** TLDR
Ubicloud explains why they use vm.overcommit_memory=2 for PostgreSQL. When OOM killer strikes, PostgreSQL's postmaster terminates ALL connections (not just the killed process) because shared memory may be corrupted. Strict overcommit converts catastrophic OOM kills into graceful ENOMEM errors. Bonus: they found a kernel bug where a one-character typo (< 0 to !) in Linux 6.5 caused 648GB of phantom committed memory on an 8GB machine.

*** Take
A one-character kernel bug (< 0 became !) hid for months and caused 648GB of phantom memory on an 8GB machine. Linus himself fixed it. This is why you don't change return conventions in mature codebases.
