*** TLDR
Netlify moved Edge Functions off a hosted V8-isolate execution service and onto Firecracker microVMs running inside its own edge network. Warm invocation median went from 25-40ms to 5-6ms, p99 improved 47.4%, and cold starts (1.2% of traffic) average about 9ms. Unikraft built the compute layer handling VM boot, snapshot, restore and scale-to-zero. The old isolate-era limits still stand: 50ms CPU per request, 512MB memory, 20MB compressed code. Nothing changes for users, same API and pricing.

*** Take
The headline number is mostly about where the code runs, not how fast it runs. Netlify deleted a network hop to an external service and the median dropped. yencabulator in the thread spots this immediately, and the post never separates execution time from transport time. The interesting part is buried: Firecracker boots in under 1ms, which means the per-request isolate model has lost its main advantage, and the 50ms CPU cap Netlify kept is now a leftover from an architecture that no longer exists.

** OpenDLSS: A Vulkan Reimplementation of Nvidia's DLSS 5 Neural Rendering Network :graphics:nvidia:vulkan:reverse-engineering:
:PROPERTIES:
:ID:       49906100
:URL:      https://github.com/maanHimself/OpenDLSS-NR
:HN_URL:   https://news.ycombinator.com/item?id=49906100
:POINTS:   136
:COMMENTS: 77
:BY:       sagacity
:END:

*** TLDR
A Vulkan reimplementation of the neural rendering network in DLSS 5 build 310.8.0, producing bit-exact output against Nvidia's original. It reconstructs the 71-block Swin/ViT architecture with FP8 (E4M3) activations on tensor cores and FP16 accumulation. Inputs are one rendered frame, Gaussian noise, a reprojected previous frame and five conditioning scalars; output is an RGB residual plus a temporal-blend logit. It ships no Nvidia code or weights, you supply those yourself. 2.8ms at 768x768 and 29.3ms at 4K on an RTX 4070 SUPER. Windows only, Ada or newer, MIT licensed. DLSS-SR upscaling is not implemented.

*** Take
Bit-exact is the claim that matters and the thing that makes this legally awkward: matching Nvidia's output to the last bit means the architecture was recovered precisely, while the weights stay on Nvidia's side of the line. That split is the whole design. It also means the project is useless to anyone who doesn't already have a DLSS install, which is probably the point. Lerc asks the better engineering question in the thread: no z-buffer input, when depth is one of the most useful conditioning signals available to a renderer.

*** TLDR
Hillel Wayne sorts TLA+ properties into what the tool handles natively and what it structurally cannot express. It checks invariants (［］P), action properties on state transitions (［］(x' >= x)), and liveness (［］<>P, <>［］P). It cannot express reachability (there exists a behavior where P holds), so you cannot ask whether a state is reachable or a game is winnable. It also cannot directly state multi-step properties like 'delete then undo restores the original', nor hyperproperties that compare two behaviors, such as proving low-power mode uses less energy than normal mode on the same action sequence. Workarounds exist via auxiliary variables and self-composition, but they bloat the model and loosen its correspondence to the real system.

*** Take
The root cause is one design decision: every TLA+ property is implicitly universally quantified over all behaviors, so existential claims have nowhere to live. That is a sharper framing than the usual 'formal methods are hard' complaint, and it explains why the workarounds feel wrong rather than merely tedious. The thread adds a real gap Wayne skips: singron points out PlusCal runs as if sequentially consistent, so weak memory models are invisible. If you reach for TLA+ to reason about atomics, that one is worth knowing before you start.
