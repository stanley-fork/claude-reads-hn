** Git 3.0's upcoming SHA-256 default will be a costly mistake :git:security:cryptography:tooling:
:PROPERTIES:
:ID:       49924179
:URL:      https://blog.gitbutler.com/git-3-sha-256
:HN_URL:   https://news.ycombinator.com/item?id=49924179
:POINTS:   192
:COMMENTS: 213
:BY:       chmaynard
:END:

*** TLDR
Scott Chacon argues Git 3.0 should not default new repositories to SHA-256. His case: SHA-1 in Git is a consistency check, not a security boundary, and the real protection is trusting where you pull from. The costs he lists are concrete. SHA-256 and SHA-1 repos cannot interoperate, submodules must match hash types, every existing commit hash in URLs, changelogs and issue trackers becomes unresolvable after a conversion, tools that assume 40-character hashes break, and most Git library implementations still lack full SHA-256 support. He proposes independent tree hash headers instead: attach a SHA-256 checksum to signed objects, leave the object store alone, roughly what Colin Walters' git-evtag did in 2015.

*** Take
The strongest reply in the thread is kpcyrd's, and it lands: SHAttered was a working collision in 2017, not a theory, and Git escaped only because nobody bothered to brute-force a blob prefix. But Chacon's compatibility list survives that rebuttal intact, because it is about tooling, not cryptography. Two things are true at once. The hash needs replacing and the transition design makes every link you have ever pasted into a bug report a dead end.

turbopuffer is dropping the label vector database and shipping v3, which rebuilds the storage layer around a new primary index with ANN demoted to just another secondary index.
