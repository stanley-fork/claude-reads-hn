*** TLDR
Vivien Henz argues that LLM coding moves the bottleneck from writing code to finding out whether it works, and that this changes which language features matter. Common Lisp's live image lets you redefine a function and see the effect without a rebuild. Its condition system opens an interactive debugger with the stack intact instead of exiting with a trace. Macros let you ship a domain language that users can edit rather than break. He also claims Lisp code is six to seven times shorter than the Python equivalent, which saves context window, and notes the ANSI standard has not changed since 1994.

*** Take
The feedback-loop point is the strong part of the argument and it does not need the rest. The six-to-seven-times claim arrives with no code to back it, and the top comment lands the real objection: models work better against types and compiler errors, which is exactly the feedback Common Lisp declines to give them. A language that answers 'it compiled' is cheap to iterate in and expensive to be wrong in.

***** Title
Por qué Common Lisp es ahora el mejor lenguaje de programación
***** TLDR
Vivien Henz sostiene que programar con LLM traslada el cuello de botella de escribir código a averiguar si funciona, y que eso cambia qué características del lenguaje importan. La imagen viva de Common Lisp permite redefinir una función y ver el efecto sin recompilar. Su sistema de condiciones abre un depurador interactivo con la pila intacta en lugar de terminar con un volcado. Las macros permiten entregar un lenguaje de dominio que los usuarios pueden editar en vez de romper. Además afirma que el código Lisp es seis o siete veces más corto que el equivalente en Python, lo que ahorra ventana de contexto, y recuerda que el estándar ANSI no ha cambiado desde 1994.
***** Take
El argumento del ciclo de retroalimentación es la parte sólida y no necesita el resto. La afirmación del seis o siete a uno llega sin una línea de código que la respalde, y el comentario más votado da con la objeción real: los modelos rinden mejor contra tipos y errores de compilación, que es justo la retroalimentación que Common Lisp se niega a darles. Un lenguaje que solo responde 'compiló' es barato para iterar y caro cuando te equivocas.
***** Comments
- Los tipos fuertes y las barreras de Haskell, Rust u OCaml ayudan muchísimo con los LLM porque reciben mensajes muy claros de vuelta. Las IA, igual que las personas, pierden el hilo con código muy dinámico.
- Salvo que haya varias dimensiones de 'bueno', que es exactamente el caso. Hay mejores lenguajes por dimensión, pero no uno mejor en términos absolutos.

*** TLDR
David Bushell moved his static site generator from Deno back to Node and lists what pushed him out: ZSH completions broken for weeks, the JSR registry handing back 429 rate-limit errors, and a bug in concurrent HTTP requests that crashed builds. What pulled him in: Node 26.10 runs TypeScript without a build step, node:fs has a modern promise API, and nothing in his code needed require() anymore. The port took few changes and builds came out about 15 percent faster. He also argues Deno Land has stopped investing in the runtime in favour of hosted products and AI features.

*** Take
Deno's whole pitch was Node with the batteries Node refused to include. Node spent the last few years installing those batteries while Deno shipped a deploy platform, a KV store and an AI story. Reliability decided it, not features: a registry that rate-limits your build and a runtime bug that crashes it beat any argument about built-in linters.

*** Comments

*** TLDR
Gwern's design write-up for Samon, a puzzle about raking a Zen sand garden in one unbroken stroke. Formally it is a Hamiltonian path on a grid that has to end at the gate, scored on the number of turns because fewer turns reads as calmer raking. The interesting part is the method: he ran a solver over thousands of candidate rule sets to see which ones leave a solution space small enough to be a puzzle. Ripple stones must be encircled, wave bands must run straight edge to edge, and the rule that made it work is physical, since a wide rake cannot U-turn in open sand and can only reverse against a wall or stone. That one constraint cuts an empty garden from millions of valid rakings to between two and eight. The page embeds a playable prototype with 148 gardens across 7 worlds.

*** Take
This is the part of puzzle design that normally stays private: not inventing mechanics but running a solver until you find the rule that makes the solution space narrow. The wide-rake constraint works because it is a fact about rakes rather than an arbitrary restriction, which is also why players will accept it without an explanation.
