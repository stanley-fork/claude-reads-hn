*** TLDR
LWN's writeup of Martin Uecker's Kernel Recipes 2026 talk. Uecker is a biomedical engineering professor who writes MRI scanner control software, and his case is that C is worth repairing rather than replacing. C23 removed K&R function definitions, support for sign-magnitude and one's-complement machines, and trigraphs, and added bit-precise integer types and checked integer operations. C2y adds case ranges, named for-loops and a _Countof() macro, and deletes roughly 45 of the remaining 100 undefined behaviors. He splits memory safety three ways: type safety, which annotations and void-pointer checking can mostly cover; spatial safety, partially solved, with the counted_by attribute handling flexible array members; and temporal safety, the hard one. His conclusion is that full memory safety in C needs either expensive runtime checking or formal verification, so the realistic path is restricted subsets plus verification tools, not a safe C.

*** Take
Removing 45 undefined behaviors is real work and worth having. The trouble is the talk's own conclusion: everything left requires runtime cost or formal proof, which is exactly where Fil-C and CHERI already sit. C is getting less dangerous at the speed a standards committee can move, and pizlonator is right in the thread that the article undersells the tools that already closed the gap.

*** Comments

Fil-C doesn't just find a lot of temporal-safety bugs. It closes off memory safety bugs for exploit writers and gives the whole language a tight semantics. The article undersells it, and CHERI too.

***** Title
Reducir el comportamiento indefinido en el lenguaje C
***** TLDR
La crónica de LWN sobre la charla de Martin Uecker en Kernel Recipes 2026. Uecker es profesor de ingeniería biomédica y escribe software de control para escáneres de resonancia magnética; su tesis es que C merece arreglarse en lugar de sustituirse. C23 eliminó las definiciones de funciones estilo K&R, el soporte para máquinas de signo-magnitud y complemento a uno, y los trigrafos, y añadió tipos enteros de precisión de bits y operaciones enteras verificadas. C2y incorpora rangos en case, bucles for con nombre y la macro _Countof(), y suprime unos 45 de los cerca de 100 comportamientos indefinidos restantes. Divide la seguridad de memoria en tres: la seguridad de tipos, que las anotaciones y la verificación de punteros void cubren en buena medida; la seguridad espacial, resuelta en parte, con el atributo counted_by para los miembros de arreglo flexible; y la seguridad temporal, la más difícil. Su conclusión es que una seguridad de memoria completa en C exige o comprobaciones costosas en tiempo de ejecución o verificación formal, así que el camino realista son subconjuntos restringidos más herramientas de verificación, no un C seguro.
***** Take
Quitar 45 comportamientos indefinidos es trabajo real y vale la pena. El problema es la conclusión de la propia charla: todo lo que queda exige coste en tiempo de ejecución o demostración formal, que es justo donde ya están Fil-C y CHERI. C se vuelve menos peligroso a la velocidad a la que puede moverse un comité de estandarización, y pizlonator tiene razón en el hilo: el artículo subestima las herramientas que ya cerraron la brecha.
***** Comments
- Fil-C no solo encuentra montones de errores de seguridad temporal. Cierra los errores de seguridad de memoria para quien escribe exploits y le da al lenguaje entero una semántica estricta. El artículo lo subestima, y a CHERI también.
- Se equivocan de árbol. C es ensamblador de alto nivel para programación de sistemas. Si añades comportamiento en tiempo de ejecución para combatir el comportamiento indefinido, los tiempos de ejecución se disparan, y el análisis estático no llega muy lejos antes de que explote el tiempo de compilación.
- "Algunas máquinas Honeywell tenían bytes de nueve bits." OS 2200 usa palabras de 36 bits y sigue siendo una plataforma soportada.

*** TLDR
Alex Lowell built a 1U rack audio interface that carries audio over ordinary Ethernet instead of USB or Dante. Six balanced TRS inputs, eight balanced outputs, 48 and 96 kHz through a Burr-Brown PCM3168A codec, plus DIN MIDI. Round-trip latency is 3.620 ms at 48 kHz with a 64-sample buffer and 1.814 ms at 96 kHz, which the page says matches an RME HDSPe AIO Pro at 48 kHz and beats it by 0.33 ms at 96. No AVB or TSN hardware required: it needs 100M full duplex, ideally a dedicated LAN, and the page recommends a $15 to $30 Intel I210 NIC. On the host it runs through JACK's netone backend or PipeWire via a pw-eth68 client, configured with an eth68ctl.py script.

*** Take
Pro audio vendors treat Linux as an afterthought, so a Linux-first interface that publishes its own round-trip numbers and ships a config script is already unusual. The sharpest question in the thread is the one the page does not answer: clock recovery. There is a BNC for syncing multiple units, but nothing explains how the receiver tracks the sender's sample clock, and that detail decides whether a three-hour session drifts.

*** TLDR
DuckLake is DuckDB's lakehouse format, MIT licensed and at v1.0 since April 2026. Data sits in plain Parquet files on local disk or object storage, and all metadata, snapshots and column statistics live in an ordinary ACID SQL database, which can be PostgreSQL, MySQL, SQLite or DuckDB itself. That arrangement gives you time travel, schema evolution, change data feeds, partitioning, filter pushdown statistics and concurrent transactions without running a dedicated catalog server, and the Parquet files stay compatible with Iceberg readers. The project says it is already in production use at a number of organizations.

*** Take
The hard part of Iceberg and Delta was never the file layout, it was running a catalog on object storage that has to behave like a transactional database. Putting the metadata in a database that already is one is the obvious answer, and the real story is how long the industry spent avoiding it. One thing buyers should hear out loud: your lakehouse's availability is now your Postgres instance's availability.
