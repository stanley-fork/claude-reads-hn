*** TLDR
OpenCode 2.0 moves the agent out of a single terminal process: a server now runs as one background service and the TUI, web and desktop clients all connect to it. The API was rebuilt from scratch and the agent can call it on itself, for example to create a git worktree. New pieces: Code Mode, a JavaScript interpreter that lets the agent compose MCP and OpenAPI tool calls into one script instead of many round trips; background tasks and subagents so async shell commands and parallel work do not block the session; a plugin system with 80+ internal plugins behind it, stable TUI plugins and hot reload, so the agent can write a plugin and load it mid-session; and an @opencode/sdk package for embedding or deploying your own build while staying compatible with the standard clients. Breaking: 1.0 plugins do not work and the server API is completely different.

*** Take
The background-service move is the actual news. It makes OpenCode an API with interfaces attached rather than a terminal app, which is why the plugin stability and the SDK matter more than Code Mode's demo. Two things the thread adds: it still uses as much RAM as 1.0 or more, and the announcement page is a WebGL showcase heavy enough to stall readers' laptops, an odd flex for a tool whose pitch is the terminal.

*** TLDR
Data for Progress put questions from DDB Needham's 1995 Life Style survey to 1,098 US adults in 2026 and compared the answers across 31 years. Entertaining at home fell from 88% to 67%, church attendance from 74% to 54%, picnics from 58% to 39%, club meetings from 45% to 26%. Playing cards is down 19 points, taking classes or seminars down 22, volunteering down 12, going out for breakfast down 13. On the other side, internet use is up about 90 points, video games 22, exercise classes 14, concerts 13, airline trips 5. The report offers no explanation for any of it and states up front that the 1995 mail survey and the 2026 web panel are not strictly comparable, so the numbers are suggestive of a trend rather than a precise estimate.

*** Take
The caveat deserves more attention than the headline. A 1995 mail survey against a 2026 web panel can manufacture a chunk of a 20-point gap on its own, so nobody should quote 88% to 67% as a measured fact. The direction is almost certainly real, Bowling Alone made the case in 2000 with better instruments, but the report publishes a wall of deltas and declines to explain any of them. The thread does the missing work: socializing moved from living rooms to paid venues, two-earner households and kids' scheduled activities ate the evenings, and the internet filled the boredom that used to push people out the door.

*** TLDR
HTTP/1 sends responses one after another on the same TCP connection, so a client only knows where the next response starts once it has consumed the current one. Before Go 1.27, closing a response body you had not read to the end meant net/http gave up on that connection and dialed a new one for the next request, which is why codebases are full of hand-rolled drain helpers. Go 1.27 makes net/http.Transport do it automatically: it drains an unread HTTP/1 body asynchronously for up to 50ms or 256KB, and skips the work when the response carries Connection: close, since reuse is impossible anyway. No API change, keep writing defer resp.Body.Close(). The post's benchmark: 100 calls to index.golang.org over HTTP/1 took about 710ms on Go 1.26 and about 150ms on 1.27.

*** Take
