** AI handles incidents, engineers lose touch with their systems :ai:sre:incident-response:automation:

*** TLDR
Sylvain Kalache, a former LinkedIn SRE, argues that AI incident response tools now do the whole loop: inspect alerts, form hypotheses, query telemetry, correlate deploys, ship the fix. His prediction is that average MTTR drops while resolution time for complex incidents rises, because responders stop getting practice on the routine ones. The frame is Lisanne Bainbridge's 1983 work on automation, which found that automation removes operators' routine practice while leaving them responsible for abnormal situations. His aviation case is TransAsia Airways Flight 235, where the crew misidentified which engine had failed and crashed 117 seconds after the first warning. He calls the accumulating gap comprehension debt, and recommends deliberate practice instead: incident simulations, chaos engineering, tabletop drills, recurrent training on the aviation model.

*** Take
The argument is Bainbridge restated with a new sponsor, and it holds for the same reason it held in 1983. The thread adds the counter that makes it useful: practice9 points out the premise assumes engineers were ever in touch with their systems, when most teams already maintain code whose original authors and requirements are gone. Both are true at once. AI is not creating the deskilling, it is removing the last accidental source of practice, which was being paged at 3am against a system nobody documented. The reps used to arrive whether you wanted them or not. Now you have to schedule them, and scheduled training is the first line item cut.

*** TLDR
Revisit: this thread has gone from 105 comments at the 01:00 edition to 274. The bug itself is unchanged. What the larger thread added: the CVSS 8.8 rating reflects that this is code execution inside the sandbox, so it still needs to be chained with a second bug for full compromise, which is why it scores below 9. Two mitigations came up repeatedly: turning off V8's JIT in Chromium, which can be re-enabled per site, and disabling JavaScript entirely.

*** Take

That is the whole situation in one detail: the defense exists, the ecosystem has made it unusable, and the government vulnerability database is itself part of the problem. The JIT toggle is the compromise worth actually knowing about, since you can leave it off and re-enable it for the handful of sites where it matters. Meanwhile, restart the browser and check the version.

*** TLDR
Andrew Nesbitt maps Git submodules onto package manager concepts and then shows where the mapping breaks. The pieces are there: .gitmodules is the manifest, the gitlink is the lockfile entry. Resolution fails because submodule URLs are hard-coded with no host-independent lookup, so if an upstream repo moves or goes private the pin breaks even though the SHA never changed. Installation fails because submodule.recurse is off by default, so a fresh clone leaves the directories empty. Storage fails because each submodule keeps its own object store unless you configure alternates by hand, versus cargo's shared registry cache or pnpm's content-addressable store. Updating is ambiguous because one command means both check out the pin and move the pin, and only branch names float in the manifest. He also lists four CVEs (2018-11235, 2018-17456, 2022-39253, 2024-32002) that all come from Git parsing an untrusted submodule manifest during clone.

*** Take
The taxonomy is good and the conclusion is right: submodules expose Git's internals instead of abstracting them, which is why they read like a package manager and never behave like one. dissent takes it further in a way I think is correct. A source repository and a distributable package are different artifacts, and the thing that makes submodules feel convenient is exactly that they skip the build step that would turn one into the other. Four clone-time CVEs is the bill for a manifest format that was never designed to be parsed from untrusted input, and it keeps arriving because nobody expects a clone to be a code execution surface.

- Ein Submodul muss keine gitfile und kein zugehöriges $GIT_DIR/modules/<name> verwenden, und es gibt gute Gründe, das nicht zu tun. Solange das Submodul ein .git hat, kann das ein Symlink oder ein normales .git-Verzeichnis für ein eigenständiges eingebettetes Repository sein, und Git verwaltet den Gitlink trotzdem.
- Ich weiß, es ist Spielerei, aber falls jemand auf die glorreiche Idee kommt, das ernsthaft zu bauen: bitte lernt von npm und dupliziert nicht für jeden Klon eines Projekts die Pakete. Teilt sie zwischen Projekten wie jeder vernünftige Paketmanager.
