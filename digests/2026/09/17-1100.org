** Breaking the 1.58-bit Barrier for Ternary LLMs :ai:llm:quantization:performance:
:PROPERTIES:
:ID:       49732931
:URL:      https://arxiv.org/abs/2609.16338
:HN_URL:   https://news.ycombinator.com/item?id=49732931
:POINTS:   210
:COMMENTS: 33
:BY:       matt_d
:END:

*** TLDR
Ternary LLMs store weights as -1, 0 or +1, and the standard five-trit packing assumes all three are equally likely, costing 1.625 bits per weight. The authors measured 29 real ternary models and found zeros make up as much as 51.5% of the weights. Their format, BITCOS, stores a dense presence bitmap plus a compacted sign vector, costing 2 minus the zero density in bits per weight: 1.485 bits on the sparsest model, and smaller than five-trit packing on 26 of the 29 models. Decoding is fast enough to use in memory, not just on disk: up to 1.28x faster matrix-vector multiply than production ternary kernels, and 1.18x end-to-end throughput on CPU, 1.27x on GPU across five platforms.

*** Take
The interesting part is not the 0.14 bits. It is that the compressed layout is the runtime layout, and it still beats the hand-tuned kernels it replaces. Most compression papers stop at the file size and hand the decode cost back to the reader.

*** TLDR
In 2014 Jake A. Smith was moving AOL's CMS from PHP 5.2 to 5.3, which dropped the pecl_http extension and with it http_build_url(). Rather than rewrite dozens of call sites, he wrote a 174-line polyfill that only registers itself when the real function is missing. It is now at nearly 20 million Packagist installs and still adds over 400,000 a month, partly through WPML, which runs on 1.5 million-plus WordPress sites, and through Debian and Ubuntu packages. He is deprecating it because it was never meant to last, because a trailing-slash bug strips the letter 'a' from paths, and because an abandoned package with that install count is an attractive supply-chain target. He points users at the PHP League's URI library or PHP 8.5's built-in URI API.

*** Take
Retiring it is the right call and the security argument is the real one: 20 million installs of unmaintained code is a handover waiting to be exploited. The trailing-slash bug that eats the letter 'a' is the part worth checking your own codebase for today.

*** TLDR
Amazon Science describes Verus, an open-source verifier that checks Rust code against formal specifications for all possible inputs rather than sampled ones. Developers annotate functions with requires and ensures clauses written in Rust-like syntax; Verus generates the proof obligations and discharges them with solvers, usually returning in under a second, which is fast enough for interactive work and for letting an LLM iterate on proofs. It handles unsafe blocks and concurrent code, including custom locking schemes with invariants. Amazon used it to prove key primitives of the Nitro Isolation Engine, which enforces VM isolation on EC2. The guarantees rest on Verus itself, the top-level specifications, the Rust standard library and the toolchain. The post gives no line counts, bug counts or proof-to-code ratios.

*** Take
The sub-second feedback loop matters more than the Nitro name-drop: verification tools fail on adoption when the check takes a coffee break, not when the logic is hard. The missing proof-to-code ratio is the number everyone deciding whether to try this actually needs.

Desarrollar código Rust demostrablemente correcto con Verus
***** TLDR
Amazon Science presenta Verus, un verificador de código abierto que comprueba código Rust frente a especificaciones formales para todas las entradas posibles, no para una muestra. Las funciones se anotan con cláusulas requires y ensures en sintaxis parecida a Rust; Verus genera las obligaciones de prueba y las resuelve con solucionadores, normalmente en menos de un segundo, lo bastante rápido para el trabajo interactivo y para que un LLM itere sobre las pruebas. Admite bloques unsafe y código concurrente, incluidos esquemas de bloqueo propios con invariantes. Amazon lo usó para demostrar primitivas clave del Nitro Isolation Engine, que garantiza el aislamiento de máquinas virtuales en EC2. Las garantías dependen del propio Verus, de las especificaciones de alto nivel, de la biblioteca estándar de Rust y de la cadena de herramientas. El texto no da líneas de código, fallos encontrados ni proporción entre prueba y código.
***** Take
El ciclo de respuesta por debajo del segundo importa más que la mención a Nitro: las herramientas de verificación fracasan en adopción cuando la comprobación se toma un descanso, no cuando la lógica es difícil. La proporción entre prueba y código que falta es justo el dato que necesita quien esté decidiendo si probarlo.

***** Title
Beweisbar korrekten Rust-Code mit Verus entwickeln
***** TLDR
Amazon Science stellt Verus vor, einen quelloffenen Verifizierer, der Rust-Code gegen formale Spezifikationen für alle möglichen Eingaben prüft statt für Stichproben. Entwickler annotieren Funktionen mit requires- und ensures-Klauseln in Rust-ähnlicher Syntax; Verus erzeugt die Beweisverpflichtungen und löst sie mit Solvern, meist in unter einer Sekunde. Das reicht für interaktives Arbeiten und dafür, ein LLM an den Beweisen iterieren zu lassen. Unsafe-Blöcke und nebenläufiger Code werden unterstützt, einschließlich eigener Sperrverfahren mit Invarianten. Amazon hat damit zentrale Primitive der Nitro Isolation Engine bewiesen, die die VM-Isolation auf EC2 durchsetzt. Die Garantien hängen von Verus selbst, den obersten Spezifikationen, der Rust-Standardbibliothek und der Toolchain ab. Zeilenzahlen, gefundene Fehler oder das Verhältnis von Beweis zu Code nennt der Beitrag nicht.
***** Take
Die Rückmeldung unter einer Sekunde zählt mehr als der Verweis auf Nitro: Verifikationswerkzeuge scheitern an der Verbreitung, wenn die Prüfung eine Kaffeepause dauert, nicht wenn die Logik schwierig ist. Das fehlende Verhältnis von Beweis zu Code ist genau die Zahl, die jeder braucht, der über einen Versuch nachdenkt.
